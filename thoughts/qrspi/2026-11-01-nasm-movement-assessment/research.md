# Research Findings

All paths are relative to the repo root. The stack is SwiftUI + SwiftData; the project is generated by
XcodeGen (`project.yml`); tests use Swift Testing (`@Test`).

## Q1: How is the `Client` model defined, and how do the edit/detail screens load, edit, validate and save it? Which sections does detail show, and how does it reach related records?

### Findings
- `Client` is an `@Model final class` (`Sources/Models/Client.swift:4-17`). Its fields are:
  - `@Attribute(.unique) id`, `name`, `phoneE164 = ""`
  - optional `goal`, `injuries`, `notes` (:10-12)
  - `isArchived = false`, `isSelf = false` (:15, the trainer's own profile), `createdAt`, `updatedAt`
- The comment at :8 says post-v0 properties carry defaults so lightweight migration works.
- `Client` declares **no** `@Relationship`.
- **Edit view model** (`Sources/Features/Clients/ClientEditViewModel.swift`):
  - It is `@Observable @MainActor`. It is initialised with a `ClientRepository`, an optional
    `existing: ClientDTO` and `isSelf` (:19-27). String fields are seeded from `existing`, with nil
    becoming "".
  - `isEditing` is true when `existing != nil` (:30).
  - `canSave` requires a trimmed, non-empty name, plus a valid phone unless `isSelf` (:32-36). Phone
    validation is `normalizeE164` in `Sources/Support/PhoneNumber.swift:5`.
  - `save()` (:38-61) builds a `ClientDTO` and maps empty strings to nil (:46-48), then calls
    `repo.upsert`. On failure it sets a fixed `errorMessage` and returns `false`.
- **Edit view** (`ClientEditView.swift`):
  - A sheet containing `NavigationStack { Form }` (:14-15).
  - Sections: Contact / "Your profile" (:16-27), Training with goal and injuries (:28-31), and Notes
    (:32-35). `ErrorBanner` comes last (:36).
  - Save calls `save()`, then `onSaved()` and `dismiss()`. It is disabled when `!canSave` (:44-55).
- **Upsert** (`Sources/Persistence/ClientRepository.swift:42-49`) fetches by id, then either calls
  `dto.apply(to:)` (`Sources/Models/DTO/ClientDTO.swift:37`) or inserts `dto.toModel()`, and saves.
- **Detail view model** (`ClientDetailViewModel.swift:7-81`):
  - `reload()` (:37-58) refreshes the client via `allIncludingArchived()`, then loads sessions via
    `sessionRepo.forClient`. It splits them with the static `splitSessions` (:61-70): upcoming are
    scheduled and in the future; recent are everything else, capped at `recentLimit = 10`.
  - `toggleArchived()` is at :72-81.
- **Detail view** (`ClientDetailView.swift`) is a `List` themed with `themedScreen`/`themedRows`.
  Sections in order:
  1. ErrorBanner (:10)
  2. Contact: phone, plus goal/injuries/notes as `LabeledContent` when non-nil (:12-26)
  3. Upcoming Sessions (:27-35)
  4. Recent Sessions (:36-44)
  5. Progress Reports, a `NavigationLink` to `ClientReportView` (:45-54)
  6. Archived label (:55-61)
- The detail toolbar `Menu` holds Edit, which opens a sheet at :96-100, and Archive/Unarchive behind a
  `confirmationDialog` at :79-95. `.task { reload() }` runs at :101.
- Sessions are reached two ways:
  - **Query:** `SessionRepository.forClient` filters on `#Predicate { $0.clientId == clientId }`,
    sorted by `startAt` descending (`Sources/Persistence/SessionRepository.swift:197-204`).
  - **Navigation:** `sessionLink` pushes `SessionRunView` (`ClientDetailView.swift:104-119`).

## Q2: How are one-to-many relationships declared, and how do repositories query child records?

### Findings
- **Owned children** use `@Relationship(deleteRule: .cascade, inverse:)` on the parent and an optional
  back-reference on the child:
  - Session → WorkoutInstance (`Sources/Models/Session.swift:30-31`, child `session` :74)
  - WorkoutInstance → PlannedEntry (:72-73, child `instance` :92)
  - Workout → WorkoutEntry (`Sources/Models/Workout.swift:8-9`, child :30)
- **Cross-entity links** are plain `UUID` fields, not relationships:
  - `Session.clientId` (`Session.swift:25`)
  - `SetRecord.workoutInstanceId` and `exerciseId` (`Sources/Models/SetRecord.swift:7-8`)
  - `WorkoutInstance.sourceWorkoutId`
  - `PlannedEntry.exerciseId`
- **Deletes follow from that split:**
  - Deleting a client is a plain `modelContext.delete` with no cascade to its sessions
    (`ClientRepository.swift:58-62`).
  - Deleting a session deletes its SetRecords explicitly with
    `modelContext.delete(model:where:)`. The comment at `SessionRepository.swift:315-316` notes the
    cascade does not reach them (:317-323, :276-282).
- **Ordering:**
  - Children carry `order: Int` (`Workout.swift:25`, `Session.swift:87`) and are sorted in memory
    when DTOs are built (`WorkoutDTO.swift:52`, `SessionDTO.swift:67`).
  - `WorkoutRepository.reorder` rewrites `order` (:66-73).
  - Upsert of an existing workout deletes and recreates its entries (:29-34).
- **Repository pattern:**
  - `@ModelActor` actors return DTOs via `.map(DTO.init)`.
  - Queries are `FetchDescriptor` + `#Predicate`. Examples:
    - `upcoming` with `fetchLimit` (`SessionRepository.swift:187-195`)
    - `seriesOccurrences` (:249-261)
    - `lastSet(clientId:exerciseId:)`: client sessions → instance ids → SetRecord `contains`, with
      `fetchLimit 1` (:361-374)
  - Children are created by appending to the parent array (`insertSession`, :395-414).
- **`ClientRepository` API** (`ClientRepository.swift:4-13`):
  - `all()` (non-archived), `allIncludingArchived()`, `search(_:)`
  - `upsert`, `setArchived(id:_:)`, `delete(id:)`, `selfClient()`

## Q3: How are SchemaV1/SchemaV2 and the migration plan structured, and how are they tested?

### Findings
- **`SchemaV1`** (`Sources/Persistence/SchemaV1.swift:8-214`) is version 1.0.0.
  - It holds frozen nested copies of all 8 models. The header (:4-7) explains that identical classes
    produce duplicate version checksums.
  - It also exposes `versionString` (:15-18).
- **`SchemaV2`** (`SchemaV2.swift:5-16`) is version 2.0.0.
  - `models` points at the live classes in `Sources/Models`.
  - Its only change is `Client.isSelf` (comment :3-4).
- **`TrainMeMigrationPlan`** (`SchemaV1.swift:216-221`) has `schemas = [SchemaV1, SchemaV2]` and one
  `.lightweight` stage. There is no custom stage.
- **`PersistenceController.makeContainer(inMemory:)`** (`PersistenceController.swift:8-23`):
  - Creates the Application Support directory.
  - Builds `ModelContainer(for: Schema(versionedSchema: SchemaV2.self), migrationPlan:
    TrainMeMigrationPlan.self, ...)`.
  - `schemaTypes` returns `SchemaV2.models` (:6).
- **`Tests/SchemaTests.swift`:**
  - Asserts model counts (8/8), version strings, and plan schema/stage counts (:5-12).
  - Asserts the container opens through the plan with 8 entities (:14-17).
  - No test migrates an actual V1 store.
- **`StoreBackup`** (`StoreBackup.swift:18-68`) is a file-level backup and is not part of the migration
  plan.
  - When `lastRunSchemaVersion` differs from the current version, it copies the store and its
    `-wal`/`-shm` files to `Backups/pre-schema-<v>/`. Only the latest backup is kept.
  - It is wired in `Sources/TrainMeApp.swift:15-34`, which calls
    `backupIfVersionChanged(... SchemaV2.versionString)`, opens the store, and on failure runs
    `restoreBackupAndRetry`.
  - Tests: `Tests/StoreBackupTests.swift`.

## Q4: How does the JSON archive map models ↔ DTOs, handle versioning, and get tested?

### Findings
- **Envelope** (`Sources/Services/Archive/ArchiveV1.swift:9-30`):
  - `ArchiveV1.schemaVersion = 1`.
  - `Envelope` holds `schemaVersion`, `exportedAt`, `appVersion`, `clients`, `exercises`,
    `workouts`, `sessions` and `setRecords`.
  - `CurrentArchive` is a typealias for it. `VersionProbe` decodes only `schemaVersion`.
  - The header (:3-7) says V1 is frozen, and that a future V2 means a new type plus a pure `migrate`
    function. V1 shares its DTOs with the live app.
- **Export** (`DataArchive.swift:29-57`):
  - Fetches every top-level model and maps each through its DTO.
  - Encodes ISO8601, `.prettyPrinted`, `.sortedKeys`.
  - Writes with `.atomic` and `.completeFileProtection`.
- **Import** (`DataArchive.swift:82-115`):
  1. Probe the version. A newer version throws `newerThanApp` (:89-91).
  2. Decode the archive (`decodeFailed` on error).
  3. For replace mode, run `deleteAll` (:119-125).
  4. Run `upsertAll`, then save. Errors roll back.
- **Upsert by id** (`DataArchive.swift:129-173`):
  - Client: `apply(to:)` or insert.
  - Exercise: field-by-field update.
  - Workout, Session and SetRecord: delete and rebuild.
  - `insertSessionGraph` preserves archive ids (:177-201).
  - In merge mode the archive wins on matching ids and local-only rows survive.
- **DTO shape** (`Sources/Models/DTO/*`):
  - Each DTO is `Codable, Sendable, Identifiable, Equatable`, with `init(_ model:)` and `toModel()`.
  - DTOs use typed values where the models store raw fields:
    - `ExerciseDTO.metrics: MetricSet` is encoded as an Int.
    - `SessionDTO.status: SessionStatus`.
    - `recurrenceData` becomes `AppRecurrence` (`SessionDTO.swift:83, 111`).
  - Parent→child graphs are nested in the JSON (Workout→entries; Session→instances→plannedEntries).
    Cross-entity links are UUIDs, and SetRecords are top-level (`SetRecordDTO.swift:5-6`).
- **Optional and new fields:**
  - Optional DTO properties decode as nil when absent (synthesized Codable).
  - `ClientDTO` deliberately excludes the device-local `isSelf` through explicit `CodingKeys`
    (`ClientDTO.swift:13-18`). This is tested in `Tests/ClientRepositoryTests.swift:124-136`.
- **`Tests/ArchiveRoundTripTests.swift`:**
  - replace round-trip (:65-97)
  - merge upserts by id (:99-127)
  - newer version rejected (:129-136)
  - unreadable data rejected (:138-143)
  - `goldenV1FixtureImports` (:145-174), which carries a "Never regenerate it" comment
- **`Tests/Fixtures/export-v1.json`** is a hand-written v1 archive:
  - It omits optional keys: the second client has no goal/injuries/notes (:17-24), and there is no
    recurrence/seriesId (:82-109).
  - It uses fixed readable UUIDs.
- **`SafeImporter.importReplacing`** (`SafeImporter.swift:14-62`):
  - Snapshots to `pre-import.json` with complete protection, then replace-imports.
  - On failure it restores the snapshot (`failedAndRestored` / `failedAndRestoreFailed`).
  - Tests: `Tests/SafeImporterTests.swift:37, 52, 72`.

## Q5: How do existing forms present structured, repeated inputs, and how do they model draft state?

### Findings
- **Controls in use:**
  - **Toggles:** `ExerciseEditView.swift:62-66` has five `Toggle`s in "Tracked metrics", each a
    separate `@State Bool`. `metrics` (:36-44) folds them into a `MetricSet` option set.
  - **Segmented picker:** `ExerciseEditView.swift:69-72`.
  - **Menu pickers:** `ExerciseEditView.swift:55`. An optional-tag picker with a "Select…" `nil` tag
    is at `SessionEditView.swift:77-82`.
  - **Steppers and DatePicker:** `SessionEditView.swift:87-91, 140`.
  - **Multi-select as tinted buttons:** the weekday row (`SessionEditView.swift:126-139`) uses
    `Set<Int>`, with selection shown via `.tint(... Theme.Colors.accent : .secondary)`. The workout
    list (:104-120) uses `Set<UUID>` with checkmark rows.
  - **`MetricStepper`** (`Sources/Features/Components/MetricStepper.swift:4-35`) is a − / numeric
    `TextField` / + control with 44pt targets and accessibility labels. `Binding` adapters are at
    :37-51.
  - **`OptionalStepper`** shows a "Set" button when nil and a stepper plus clear button otherwise.
    **`AdaptiveLabeledRow`** uses `ViewThatFits` to switch between HStack and VStack
    (`WorkoutBuilderView.swift:179-227`).
- **Grid/table:** `SetTableView.swift`.
  - A header plus rows that are logged, draft or placeholder (:46-55, 76/94/137).
  - Columns come from the tracked metrics (:39).
  - One shared `stepperStrip` edits whichever cell is focused (:152-179).
  - The layout stacks at accessibility text sizes (:41, :184, :219).
- **Draft models (three patterns):**
  1. `@State` fields seeded in `init` from `existing` (`ExerciseEditView.swift:20-34`,
     `SessionEditView.swift:51-61`).
  2. An `@Observable @MainActor` view model with plain vars, `canSave`, `isEditing` and
     `save() async -> Bool` (`ClientEditViewModel.swift`, `WorkoutBuilderViewModel.swift:6-86`).
  3. A value-struct draft, `SetDraft: Equatable, Sendable` (`Sources/Features/Session/SetDraft.swift:4-23`).
- **Dirty tracking** exists only in `SetTableView` (`draftTouched`, :18, :301-305). Edit forms have
  no dirty flag.
- **Cancel** is a plain `dismiss()` everywhere. There is no `interactiveDismissDisabled`.
  `confirmationDialog` and `.alert` are used only for delete, archive, reset and import.
- **Save shape** is the same in all four forms: `Button("Save") { Task { if await save() { onSaved();
  dismiss() } } }.buttonStyle(.borderedProminent).disabled(!canSave)`
  (`ExerciseEditView.swift:82-93`, `ClientEditView.swift:44-55`, `WorkoutBuilderView.swift:53-64`,
  `SessionEditView.swift:162-173`).
- **Errors:** an `errorMessage` String is rendered by `ErrorBanner` as the final Form section
  (`Components/ErrorBanner.swift:4-17`).
- **Presentation:**
  - Create and edit forms are sheets wrapping their own `NavigationStack`, using `isPresented` or
    `item:` (e.g. `ClientListView.swift:46`, `ExerciseListView.swift:56`).
  - Nested sheets use `.presentationDetents([.medium])` (`WorkoutBuilderView.swift:71-80`).
  - Read and detail screens are pushed with `NavigationLink`.
- **Previews:** `Sources/Support/PreviewFixtures.swift`.
  - It is a `@MainActor enum` of static DTOs.
  - `repositories()` is backed by an in-memory seeded container (:114-156). It is built outside
    `#Preview` because `@ModelActor` initialisers aren't visible inside the macro (:111-113).
  - Example: `ClientEditView.swift:61-69`.
- **Theme** (`Sources/Support/Theme.swift`):
  - Colors (:5-15), Fonts (:17-24), Spacing (:26-31), Radius (:33-35).
  - `themedScreen()` and `themedRows()` (:38-49) are applied on list and detail screens, not on edit
    sheets.

## Q6: How do reporting queries, ClientReportView and ReportExporter build and share per-client output? Are there cross-date comparison patterns?

### Findings
- **Query protocol:** `ReportingQueries` (`Sources/Persistence/ReportingQueries.swift:122-142`) is
  implemented by the `@ModelActor SwiftDataReportingQueries` (:144).

  - Also provided: `personalBest` (:171-175), `historyBySession` (:177-195), `consistency`
    (:197-214), and volumes, including weekly buckets (:237-248).
- **Data honesty:** set-based queries use completed sessions only (:282-315).
- **Windows:** `ReportWindow` is `fourWeeks`, `twelveWeeks` or `all` (:42-62).
- **`ClientReportViewModel`** loads top exercises (:30-43) and the windowed metrics (:65-71). The
  default window is `.twelveWeeks`.
- **`ClientReportView`** sections, in order (`ClientReportView.swift:10-66`):
  1. Window picker
  2. Consistency
  3. Weekly volume chart
  4. Session volume rows
  5. Top exercises, each a `NavigationLink` to `ExerciseReportView`
     (`ExerciseReportView.swift:20-42`)
- **Charts:** Swift Charts `ExerciseProgressChart` (LineMark + PB PointMark) and `VolumeChart`
  (BarMark) (`ExerciseReportView.swift:100-190`). Both show "Not enough data yet" below 2 points.
- **`ReportExporter`** (`Sources/Services/ReportExporter.swift`):
  - Renders PDF and PNG only (:4-7) via `ImageRenderer` at 612×792, scale 3 (:14-49).
  - Output goes to `tmp/Reports` with complete protection (:46-47). Names are sanitized (:61-64).
  - Pages are `ExerciseReportPage` (:68-102) and `ClientOverviewPage` (:105-138), forced to the light

- **`ShareReportMenu`** (`Components/ShareReportMenu.swift:8-14`) holds two `ShareLink`s. Report
  files are swept on disappear (`ClientReportView.swift:76-80`).
- **Cross-date comparison:**
  - Trends exist: per-day line charts, weekly bars, and per-session history.
  - Previous-vs-current exists only as the "Prev" set in session recording
    (`SessionRunViewModel.swift:26-28, 87` → `SetTableView.swift:68`).
  - No side-by-side comparison of two chosen dates exists in the reporting files.
- **Tests:**
  - `Tests/ReportingTests.swift` has 17 query cases (e.g. :88, :187, :251).
  - `Tests/ReportExporterTests.swift:11-35` covers file output and sanitizing.
  - No view or chart tests.

## Q10 (external): Recommended intake data points; waiver contents; e-signature and retention

Sources are mostly secondary (NFPT, NASM blog, study guides, vendor and law-firm blogs). Primary
NASM/ACE/ACSM manuals and the official PAR-Q+ text were **not** retrieved. Treat attributions as
"per secondary sources".

### Findings: intake
- **Screening documents** (NFPT, https://nfpt.com/pre-screening-for-personal-trainers-guide/):
  - PAR-Q / PAR-Q+.
  - ACSM Preparticipation Screening Questionnaire.
  - Health History Questionnaire (HHQ), covering personal and family medical history, lifestyle habits
    and prior exercise experience.
- **HHQ contents** in study guides:
  - Medical history: past injuries, surgeries, chronic conditions, current medications and
    supplements, family history of premature cardiovascular disease.
  - Symptoms: angina, dyspnea, syncope, ankle edema.
  - Lifestyle: occupation, sleep, stress, tobacco, alcohol, hobbies and recreation.
  - Documentation is dated, with trainer action and referral/clearance status noted.
  - URLs: https://open-exam-prep.com/study-guides/nasm-cpt/05-assessment-intake-risk-and-physiological-testing/par-q-health-history-lifestyle-questionnaire-and-documentation
    and https://open-exam-prep.com/study-guides/acsm-cpt/chapter-2-health-screening/health-history-medical-clearance
- **Contact data:** physician name and contact, emergency contact, age, gender, height and weight.
  This appears only in a low-authority flashcard source.
- **Baseline measurements:**
  - Resting HR, BP (above 140/90 flagged), height and weight / BMI, waist circumference / waist-to-hip
    ratio, body composition.
  - Baseline fitness tests: push-up, plank, timed walk or run.
  - NFPT and NASM guides say this data is for tracking progress, not diagnosis.
- **PAR-Q+:**
  - A 7-question yes/no general section. Any YES leads to follow-up questions on condition categories
    (arthritis, osteoporosis, back, cancer, and others). Review at least every 12 months.
  - The questions cover: heart condition or high BP; chest pain; dizziness or loss of consciousness;
    other chronic condition; medication for a chronic condition; bone, joint or soft-tissue problem;
    doctor-advised supervised activity only. The exact wording of question 7 is unconfirmed.
  - Older CSEP forms state the form may not be altered and may be copied only in its entirety. The
    official form is at eparmedx.com / csep.ca.
- **Clearance logic** (ACSM/ACE via study guides): a YES leads to follow-ups, and medical clearance
  is needed only if those still flag risk. Inactive, asymptomatic adults with no known
  cardiovascular, metabolic or renal disease generally need no clearance.
- **NASM overhead squat** (https://www.nasm.org/resource-center/blog/training/how-to-perform-an-overhead-squat-assessment-osa):
  - Compensation → likely overactive/underactive muscles:
    - feet flatten or turn out → calves overactive
    - knees cave in → adductors and TFL overactive, glute medius underactive
    - forward lean or arms fall forward → calves, hip flexors and lats overactive; core and scapular
      stabilizers underactive
  - The heel-elevated variation isolates ankle involvement.
  - Re-test every 4–8 weeks. Stop and refer on pain, numbness or tingling.
  - The assessment is described as a screen, not a diagnosis. The full NASM solutions table and the
    single-leg squat mapping were not retrieved.

### Findings: waivers
- **Elements** (NFPT summarising Pepper Hamilton LLP, https://nfpt.com/liability-waiver-forms-legal-position-personal-trainer/):
  - Explicit release that names "ordinary negligence".
  - Assumption of risk and waiver of claims.
  - Conspicuous formatting.
  - A standalone document, separate from the training agreement.
  - A reading acknowledgement and initials above the signature.
  - An integration clause.
- **Informed consent** is a separate document from the waiver. It covers purpose, risks, benefits,
  questions, voluntary participation and the right to stop, and confidentiality. It does not protect
  against negligence claims. A waiver does not replace health screening.
- **Other clauses** (indemnification, emergency-treatment consent, photo consent, governing law,
  severability, minor/guardian) appear only in vendor templates. No authoritative source was found.
- **Enforceability** varies by state. Waivers generally cover ordinary negligence, not gross
  negligence. Sources advise consulting a lawyer familiar with the state and the fitness industry, and
  NFPT also recommends carrying insurance. Corrigan v. Musclemakers is cited as a case where the
  waiver failed.

### Findings: e-signatures, retention, HIPAA
- **ESIGN/UETA** (vendor blog, https://blog.pushpress.com/2017/03/29/digital-waivers-the-esign-act-and-ueta-compliance):
  - Intent to sign.
  - Consumer consent to electronic records, with the right to withdraw.
  - Records must be retrievable and accurately reproducible.
  - The signed version must stay unchanged even if the template later changes, so historical versions
    are kept.
  - Each signature is linked to the document, with an audit trail of time and date.
  - The statute text was not verified.
- **Retention:** keep screening forms, consents, waivers and notes 3–7 years after the relationship
  ends, depending on the state. For minors, keep them past age 18. This comes from a study guide, not
  a statute.
- **HIPAA** generally does not apply to independent trainers. It may apply in clinical or
  medical-fitness settings.

## Cross-Cutting Observations
- **Layering:** `@Model` classes in `Sources/Models` → DTO structs in `Sources/Models/DTO` →
  `@ModelActor` repositories returning DTOs → `@Observable @MainActor` view models → SwiftUI views.
  Views never touch `@Model` objects directly.
- **Owned vs cross-entity links:** cascade relationships are used only for parent-owned children.
  Everything else links by UUID. This shapes deletes, which are explicit, and the archive layout,
  which nests owned graphs and keeps UUID-linked entities top-level.
- **Persisted-model changes ripple** through:
  - a frozen copy in `SchemaV1`, the live class in `SchemaV2`, and the migration plan
    (`SchemaV1.swift:216-221`)
  - `StoreBackup` version keys
  - the DTO and its `CodingKeys`
  - archive export/upsert/deleteAll (`DataArchive.swift`)
  - the golden fixture test
  - `PreviewFixtures`
- **Option sets for multiple booleans:** `MetricSet` packs flags into an Int, both in the model
  (`metricsRaw`) and in JSON (`"metrics": 7`).
- **Edit forms share one shape:** sheet + `NavigationStack` + `Form`, `canSave`-gated Save,
  `ErrorBanner` last, Cancel without confirmation.
- **Sensitive files** (exports, reports, snapshots) consistently use complete file protection and are
  swept when no longer needed.
